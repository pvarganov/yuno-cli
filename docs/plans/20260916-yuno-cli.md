# yuno-cli — CLI for the full Yuno API

## Overview

Build `yuno-cli`, a Go command-line client covering **every** operation of the public Yuno REST API
(OpenAPI 3.1.0: 119 paths, 172 operations, 31 resource groups).

Problem it solves:
- Yuno's own MCP server exposes only 39 tools (payments, customers, checkout sessions, subscriptions,
  installment plans, recipients, payment links). Everything else — routing, connections,
  organizations, webhooks, reports, payouts, sellers, PCI proxy, banking connectivity — is reachable
  only through the dashboard or hand-rolled `curl`.
- Overgear needs scriptable, auditable access to Yuno for support, debugging and configuration
  review (the immediate driver: reading card routing rules via `GET /routing`).

Key benefits:
- One binary, all 172 operations, pipe-friendly JSON output for `jq`.
- Named profiles (sandbox / prod-US / prod-EU) so the same command can be pointed at the right
  environment without editing env vars.
- Write operations are confirmed by default, so a prod key cannot silently create a payment.

Integration with the existing system: the project lives at `~/repo/yuno-cli`, next to
`~/repo/slack-threads`, and copies the architecture of `~/overgear/linear-cli` and
`~/overgear/orx-cli` verbatim (cobra, stdlib testing, httptest, golangci-lint v2, goreleaser,
Homebrew tap `pvarganov/homebrew-tap`).

**Patterns found:**

  `<TOOL>_CONFIG_DIR` and `<TOOL>_API_ENDPOINT` overrides used exclusively by tests.
- Output: `Formatter` interface, `NewFormatter(jsonMode)`, JSON via `MarshalIndent`, tables via
  reflection over flat view structs.
- Tests: stdlib `testing` only — **testify is banned**; `httptest.NewServer`; no mock libraries;
  no golden files; `go test -race`.
- Build: `make build` depends on `lint`; direct `go build` is forbidden.
- Docs convention: the external API spec is checked into `docs/` as the source of truth
  (`docs/schema.graphql` in linear-cli → `docs/yuno-openapi.json` here).

## Development Approach

- **Testing approach**: TDD (tests first) — write the failing test, then the implementation.
- Complete each task fully before moving to the next.
- Make small, focused changes.
- **CRITICAL: every task MUST include new/updated tests** for code changes in that task
  - tests are not optional - they are a required part of the checklist
  - write unit tests for new functions/methods
  - write unit tests for modified functions/methods
  - add new test cases for new code paths
  - update existing test cases if behavior changes
  - tests cover both success and error scenarios
- **CRITICAL: all tests must pass before starting next task** - no exceptions
- **CRITICAL: update this plan file when scope changes during implementation**
- Run `make test` and `make lint` after each change (`make build` runs lint first by design).
- Maintain backward compatibility of command names and flags once a resource group ships.

Project-specific rules inherited from `linear-cli`/`orx-cli` CLAUDE.md — mandatory:
- stdlib `testing` only, **no testify**, no mock libraries; HTTP mocked with `httptest.NewServer`.
- Wrap every error with context: `fmt.Errorf("list routings: %w", err)`, lowercase, no trailing dot.
- Pointers (`*string`, `*int`) for optional request fields; `map[string]any` for PATCH bodies so
  "absent" and "zero" stay distinguishable.
- Functions ≤ 80 lines / 50 statements, cyclomatic complexity ≤ 10, nesting ≤ 5.
- Imports in three groups: stdlib / external / local.
- All code, comments, docs and user-facing strings in English.

## Testing Strategy

- **Unit tests**: required for every task (see Development Approach above).
  - `internal/api` — internal test package (`package api`) so `sleep` can be swapped; every client
    method gets a success test and at least one error test (4xx body parsing, 5xx retry,
    context cancellation).
  - `internal/cmd` — external test package (`package cmd_test`), driving the real root command with
    `root.SetArgs(...)` against an `httptest` server wired in via `YUNO_API_ENDPOINT`.
  - `internal/config`, `internal/output`, `internal/confirm` — table-driven unit tests.
- **Coverage gate**: a per-group task is done only when every operation listed for that group in
  `docs/yuno-operations.txt` has a command test that asserts method, path and body.
- **E2E tests**: not applicable — no UI. A manual smoke script against the sandbox environment is
  listed under Post-Completion instead.

## Technical Details

**Command shape** — `yuno-cli <resource> <action> [id] [flags]`, e.g.:

```
yuno-cli routing list --account-id <uuid> --payment-method CARD
yuno-cli payment get <payment_id> --json | jq '.transactions[].provider_data'
yuno-cli customer update <id> --email new@example.com
yuno-cli payment create --file payment.json --idempotency-key <uuid>
yuno-cli raw POST /sellers --file seller.json
```

**Persistent flags**: `--json`, `--profile`, `--verbose`, `--yes`, `--unmask`, `--timeout`.

**Request bodies**: large payloads (`POST /payments`, `POST /routing`) come from `--file` or stdin;
small, frequently-used fields also get named flags. PATCH bodies are built as `map[string]any` from
`f.Changed(...)` so an explicit empty string is distinguishable from an omitted field.

**Auth headers** sent on every request: `public-api-key`, `private-secret-key`, plus `X-Account-Code`
and `X-Organization-Code` when the profile defines them, plus `X-Idempotency-Key` on POST/PATCH.

**Endpoints**: `sandbox` → `https://api-sandbox.y.uno/v1`, `prod-us` → `https://api.y.uno/v1`,
`prod-eu` → `https://api.eu.y.uno/v1`; `YUNO_API_ENDPOINT` overrides all three (used by tests).

**Exit codes** (from orx-cli): `0` success, `1` API error, `2` confirmation declined,
`3` config/input error.

**Processing flow**: cobra command → `newClientFromFlags` (config + profile + env) → build request →
confirmation gate for non-GET → `api.Client.Do` (auth headers, idempotency, retry) → decode →
`output.Formatter` → stdout.

## Post-Completion

*Items requiring manual intervention or external systems - no checkboxes, informational only*

**Manual verification**:
- Smoke-test every resource group against the **sandbox** environment with real sandbox keys; the
  test suite only proves the client speaks the right HTTP, not that Yuno accepts it.
- Confirm the confirmation gate behaves correctly in a real terminal (TTY) and under `| cat` (non-TTY).
- Verify that no card data or API key ever reaches stdout/stderr, including under `--verbose`.

**External system updates**:
